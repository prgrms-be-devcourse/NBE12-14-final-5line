# OUTPICK 상세 기획·설계안

**OUTPICK은 스포츠·액티비티 장소를 찾고, 방문 판단에 필요한 정보를 확인하는 웹 서비스입니다.**

- **지도:** 카카오 지도 기본안
- **데이터:** 한국관광공사 관광정보를 후보로 확보하고, 공식 안내를 검수해 공개.
- 해양수산부 API 연결
- **콘텐츠:** 사진 후기 포함, 사용자 숏폼 업로드 (고려사항)
- **실시간:** SSE로 변경 알림·열람 인원 전달, HTTP로 상태 갱신.
- **서버:** 단일 Spring Boot 애플리케이션으로 시작.
- **Redis·Kafka:** 필수 도입하지 않고 측정·운영 요구가 생기면 검토. (필요하면 도입)

## 1. 서비스 개요

### 서비스명

**OUTPICK — 아웃픽**

**이번 주말, 밖에서 뭐 하지?**

### 한 줄 소개

지역·종목·시즌에 맞는 스포츠·액티비티 장소를 지도와 목록에서 탐색하고, 사진·후기·공식 안내를 확인하는 정보 제공 서비스입니다.

### 상세 소개

스키·서핑·스노클링·낚시 등 다양한 활동을 지역과 종목으로 찾습니다. 사용자는 지도에서 위치를 확인하거나 전체 목록에서 장소를 둘러보고, 관심 장소를 저장하거나 친구에게 링크를 보낼 수 있습니다.

장소 정보에는 출처와 확인일을 표시합니다. 사용자 후기와 운영자가 확인한 정보를 구분하고, 잘못된 정보는 제보할 수 있습니다.

### 해결하려는 문제

1. **탐색 경로가 분산됨**

   지도·검색·블로그·공식 홈페이지에서 같은 장소를 반복 확인해야 합니다.

2. **종목을 정하기 전 탐색이 어려움**

   “강원에서 뭘 할까?”처럼 활동부터 고르고 싶은 상황을 지원합니다.

3. **정보의 최신성을 판단하기 어려움**

   오래된 후기와 현재 공식 안내가 섞여 보일 수 있습니다.

4. **지도와 설명을 오가야 함**

   위치 관계와 장소 설명을 같은 검색 결과에서 확인하도록 연결합니다.


### 목표 사용자와 이용 상황

- 주말에 할 야외 활동을 찾는 사람.
- 종목은 정했지만 방문할 장소는 정하지 못한 사람.
- 처음 가는 장소의 위치·소개·이용 경험을 확인하려는 사람.
- 친구에게 방문 후보를 공유하려는 사람.

### 방문·저장·공유·재방문의 이유

- **방문:** 활동 장소를 찾기 위해.
- **저장:** 여러 후보를 나중에 다시 확인하기 위해.
- **공유:** 일행에게 같은 장소 정보를 보여 주기 위해.
- **재방문:** 저장한 후보 확인, 새 활동 탐색, 중요한 정보 변경 확인.

### 제공 범위

- 장소 탐색·상세 정보.
- 사진 후기.
- 저장·링크 공유.
- 제보·신고.
- 확인된 정보 변경 알림.
- 현재 상세 화면 열람 인원.

예약·결제·환불·크레딧, 장비·강습 관리, 모임방·투표·채팅은 포함하지 않습니다.

### 약점과 검증할 가설

**가장 큰 약점은 기존 지도·검색보다 더 편한 이유가 약할 수 있다는 점입니다.**

실시간 열람 인원만으로 이를 해결할 수는 없습니다. 먼저 검증할 가설은 다음입니다.

> “지역과 활동을 고를 때, 여러 검색 결과를 오가는 것보다 OUTPICK에서 필요한 정보를 적은 과정으로 확인할 수 있다.”
>

## 2. 사용자 흐름과 화면

### 비회원 기본 흐름

1. 접속하면 등록된 전체 장소가 보입니다.
2. 지역·종목·시즌으로 검색합니다.
3. 목록 또는 지도에서 장소를 선택합니다.
4. 상세에서 사진·소개·위치·공지·후기를 확인합니다.
5. 공식 홈페이지·길찾기로 이동하거나 장소 링크를 공유합니다.

로그인 안내가 검색과 상세 조회를 막지 않도록 합니다.

### 회원 흐름

- `저장` 선택 → 로그인 필요 시 로그인 → 원래 장소로 복귀.
- `후기 작성` → 방문일·종목·본문·사진 입력 → 검증 후 게시.
- `정보 수정 제보` → 항목·내용·근거 입력 → 처리 상태 확인.
- 알림함 → 관심 장소 변경 확인 → 해당 상세로 이동.

### PC 화면

- 상단: 검색창.
- 두 번째 줄: 카테고리·지역·시즌·정렬.
- 본문 왼쪽: 큰 사진의 **2열 장소 목록**.
- 본문 오른쪽: 지도.
- `전체 목록` 전환 시 지도 영역까지 목록으로 활용.
- 카드 선택과 지도 마커 선택을 연결.

### 모바일 화면

- 목록 중심.
- 하단 고정 `지도 보기`.
- 지도에서 장소를 선택하면 하단 카드.
- 필터는 별도 패널.
- 상세는 독립 화면.
- 저장·공유 버튼은 접근하기 쉬운 위치에 배치.

### 상태 유지

검색 조건은 URL에, 목록 스크롤은 화면 상태에 보관합니다.

- 새로고침: 검색 조건 복원.
- 뒤로 가기: 기존 조건·스크롤 복원.
- 장소 공유 링크: 해당 상세로 바로 이동.
- 로그인 후: 원래 행동을 이어갈 수 있도록 복귀.

### 주요 문구와 예외 화면

- 검색창: **“지역이나 액티비티를 검색해 보세요”**
- 지도: **“이 지역 다시 검색”**
- 공식 링크: **“공식 홈페이지에서 확인”**
- 정보 변경: **“장소 정보가 업데이트됐어요”**
- 빈 결과: **“조건에 맞는 장소가 없어요. 지역이나 종목을 바꿔 보세요.”**
- 지도 장애: **“지도를 불러오지 못했어요. 목록으로 계속 살펴볼 수 있어요.”**
- 실시간 장애: **“실시간 정보 연결을 확인하고 있어요.”**
- 위치 권한 거부: **“지역을 직접 선택해 주세요.”**

사진이 없으면 다른 시설 사진을 대신 쓰지 않고, 종목별 중립적인 대체 이미지를 사용합니다. 후기가 없어도 기본 정보는 정상 제공됩니다.

## 3. 상세 기능 명세

### F01. 장소 탐색·검색

- **이유:** 원하는 활동과 지역의 후보를 찾도록 함.
- **동작:** 검색어·필터 입력.
- **입력:** 지역, 종목, 시즌, 검색어, 정렬, 페이지.
- **출력:** 장소 카드·결과 수·적용 조건.
- **서버 규칙:** 공개 상태만 반환, 페이지 크기 제한.
- **예외:** 잘못된 조건은 안내하고, 빈 결과는 정상 응답.
- **권한:** 비회원 가능.
- **완료 기준:** 같은 조건에서 목록과 지도가 같은 모집단을 사용.

### F02. 장소 상세

- **이유:** 방문 후보를 판단.
- **동작:** 카드·마커·공유 링크 선택.
- **입력:** 장소 ID.
- **출력:** 사진·소개·주소·종목·공지·출처·공식 링크.
- **규칙:** 사용자 후기와 검수 정보를 분리.
- **예외:** 운영 종료는 상태 안내, 비공개는 조회 제한.
- **권한:** 공개 장소는 비회원 가능.
- **완료 기준:** 확인되지 않은 정보와 갱신 시점을 구분할 수 있음.

### F03. 관심 장소

- **이유:** 검색을 반복하지 않고 후보를 다시 확인.
- **동작:** 저장·해제·내 목록 조회.
- **입력:** 장소 ID, 알림 설정.
- **출력:** 현재 저장 상태.
- **규칙:** 사용자·장소 조합당 하나.
- **예외:** 연속 클릭도 중복 행을 만들지 않음.
- **권한:** 회원.
- **완료 기준:** 새로고침·다른 기기에서 동일 계정의 저장 상태 유지.

### F04. 링크 공유

- **이유:** 기존 메신저에서 장소를 전달.
- **동작:** 공유 또는 링크 복사.
- **출력:** 장소 고유 URL.
- **규칙:** 로그인·방 생성 없이 공개 상세 열람.
- **예외:** 공유 기능 미지원 시 링크 복사.
- **완료 기준:** 검색 화면을 거치지 않고 해당 장소로 진입.

공유 미리보기는 정적 정보가 들어간 서버 제공 페이지로 구성할 수 있습니다. 위치정보·개인 식별값을 공유 URL에 넣지 않습니다.

### F05. 사진 후기

- **이유:** 특정 시점의 실제 경험을 참고.
- **입력:** 방문 날짜, 종목, 본문, 검증 완료 사진 ID.
- **출력:** 게시된 후기.
- **규칙 제안:** 본문 20~2,000자, 사진 최대 5장, 미래 방문일 불가.
- **예외:** 업로드 실패 시 초안 유지, 수정 충돌 시 최신 내용 확인.
- **권한:** 회원 작성, 본인 수정·삭제.
- **완료 기준:** 다른 사람의 글·사진을 변경하거나 자신의 글에 연결할 수 없음.

### F06. 정보 오류 제보

- **이유:** 오래되거나 틀린 정보를 수정.
- **입력:** 대상 항목, 설명, 근거 URL 또는 사진.
- **출력:** 접수 번호·처리 상태.
- **규칙:** 접수만으로 공개 정보 변경 금지.
- **예외:** 중복 제보는 운영자가 연결해 처리.
- **권한:** 회원 접수, 운영자 검수.
- **완료 기준:** 반영·반려 사유와 변경 근거가 남음.

### F07. 신고

- **이유:** 부적절한 사용자 콘텐츠 대응.
- **입력:** 후기 ID·사유.
- **규칙:** 동일 사용자·후기 신고 중복 제한.
- **예외:** 신고 수만으로 자동 영구 삭제하지 않음.
- **권한:** 회원 신고, 운영자 처리.
- **완료 기준:** 숨김·복구·처리자·사유 기록.

### F08. 열람 인원·변경 알림

- **이유:** 현재 화면의 변화와 중요한 소식을 전달.
- **입력:** 열람 상태·연결, 운영자가 확정한 변경.
- **출력:** 인원 스냅샷·업데이트 신호·개인 알림.
- **규칙:** 숫자는 현장 혼잡도와 구분, 알림 원본은 DB에 보관.
- **예외:** 실시간 실패 시 정보 탐색 유지.
- **완료 기준:** 재접속 후 현재 상태를 복구하고, 중복 알림을 만들지 않음.

## 4. 검색·지도 설계

### 검색어 해석

자동완성은 유형을 구분합니다.

- `지역: 강원특별자치도`
- `종목: 스키`
- `장소: 특정 시설`

선택하면 ID 기반 필터로 변환합니다. 일반 자유 입력은 장소명·별칭 검색으로 처리합니다.

문장형 AI 검색은 범위에서 제외합니다.

### 조건 결합

- 지역·종목·시즌·검색어 사이는 **AND**.
- 여러 종목을 고르면 종목 사이에는 **OR**.
- 장소 하나가 여러 종목을 제공해도 결과에는 한 번만 표시.

### 종목과 시즌

`장소 → 제공 종목 → 해당 종목의 시즌`으로 연결합니다.

예를 들어 한 시설의 여름 카약 정보가 겨울 스키 검색에 잘못 적용되지 않도록 **같은 종목 관계 안에서 시즌을 검사**합니다.

시즌 미확인은 ‘사계절’로 처리하지 않습니다.

### 지도 영역과 지역

- 지도 이동만으로 검색하지 않음.
- `이 지역 다시 검색`에서 영역 조건 확정.
- 지역 필터와 영역 조건은 교집합.
- 적용된 `현재 지도 영역` 조건을 화면에 표시·해제 가능.
- 지역을 바꾸면 이전 지도 영역 조건은 초기화.

### 목록·마커 API 분리

- 목록: 20개씩, 최대 50개 제안.
- 지도: 같은 필터의 마커 또는 영역별 집계.
- 현재 목록의 20개만 지도 전체 결과인 것처럼 표시하지 않음.
- 마커 상한 초과 시 잘라내지 않고 집계·확대 안내.

### 정렬

- 기본: 이름순.
- 추가: 최근 등록순.
- 위치 동의 시: 거리순.

거리순은 **직선거리**이며 이동시간이 아닙니다. 동일 정렬값에는 장소 ID를 추가 기준으로 사용합니다.

### 응답 순서·화면 성능

- 이전 검색 요청 취소 또는 최신 요청 번호 검사.
- 늦은 응답이 새 검색을 덮어쓰지 않도록 함.
- 지도 이동은 명시적 재검색으로 호출량 제어.
- 사진 썸네일·지연 로딩·이미지 영역 크기 고정.
- 마커 변경분 반영, 지나친 전체 재생성 방지.
- 긴 목록은 페이지 추가 또는 필요 시 가상화.
- 모바일에서 지도와 대량 사진을 동시에 과도하게 렌더링하지 않음.

**서버 부하와 브라우저 화면 버벅임은 별도 시험합니다.**

## 5. 데이터 확보와 최신성

### 실제 활용 후보

**한국관광공사 국문 관광정보 서비스**

공식 안내상 지역·위치·키워드 검색, 공통·소개·이미지·동기화 정보 등을 제공합니다. 다만 모든 스포츠 시설과 필요한 필드가 채워져 있다는 의미는 아닙니다. 공공데이터포털

확보 후보는 다음입니다.

- 외부 콘텐츠 ID.
- 장소명·주소·좌표.
- 분류.
- 소개·대표 이미지·홈페이지.
- 원본 수정 시각.

**각 필드의 실제 제공 여부와 결측률은 샘플 조회로 확인해야 합니다.**

### 출처별 역할

- **공공데이터:** 초기 후보·기본 정보.
- **지도 API:** 지도 표시·주소 확인·장소 찾기 보조.
- **시설 공식 홈페이지:** 운영·중단·공식 공지 검수.
- **사용자 제보:** 재검토가 필요한 단서.
- **사용자 후기:** 특정 방문 시점의 개인 경험.

지도 검색 결과를 그대로 자체 영구 DB로 복제하거나, 공식 홈페이지 사진을 자유롭게 재사용할 수 있다고 가정하지 않습니다.

### 추천 초기 범위

- **강원·경기 중심.**
- 스키·스노보드를 주력으로, 공식 정보를 확보할 수 있는 일부 다른 종목 포함.
- 공개 장소 **20~30곳을 작업 목표**로 설정.
- 첫 3일에 샘플 5곳의 필수 정보·사용 권한을 확인한 뒤 수량 조정.
- 데이터 없는 카테고리는 비활성 또는 미노출.
- 전국 지도를 제공하더라도 실제 데이터 범위를 명시.

전국 수천 곳을 급하게 채우는 것보다 확인 가능한 자료를 제공하는 쪽을 우선합니다.

### 저장·갱신 구조

외부 데이터는 바로 공개 DB에 덮어쓰지 않습니다.

1. 원본 ID 기준 후보 수집.
2. 기존 장소와 대응 확인.
3. 변경된 필드만 비교.
4. 운영자 수정값과 충돌하면 검토 대상으로 전환.
5. 확인 후 공개 버전 갱신.
6. 필요한 경우 변경 알림 생성.

### 중복 판단

- 동일 외부 ID: 같은 출처의 중복 방지.
- 이름·좌표·주소 유사성: 병합 후보 생성.
- 근처에 있다는 이유만으로 자동 병합 금지.
- 시설과 그 안의 별도 사업체는 구분 가능.
- 병합된 URL은 대표 장소로 안내.

### 운영 시간·공지

- 반복되는 주간 시간과 기간 한정 공지를 구분.
- 휴일 예외를 표현하지 못하면 ‘현재 영업 중’ 배지 제외.
- 기본 화면에는 `공식 운영 안내`와 확인일 제공.
- 임시 중단·운영 종료는 검수된 근거와 유효 시각 기록.

### 점검 주기 제안

- 제보·신고: 운영일마다 확인.
- 지원 API 변경 목록: 하루 1회부터 검토.
- 시즌 핵심 장소: 주 1회 수동 재확인.
- 중요 공지: 발견·제보 시 우선 검수.
- 링크 점검: 주 1회, 실패 즉시 폐업 처리하지 않음.
- 오래된 정보: 30일 등 기준을 정해 재검토 목록에 표시.

외부 URL 자동 조회는 HTTP(S)·대상 호스트·리디렉션·응답 크기를 제한하고, 내부망 주소 접근을 차단합니다.

현재는 구형 AI NAVER API 안내 대신 **새 Maps 상품 기준**으로 확인해야 합니다. 공식 Maps 안내

### Google Maps Platform

해외 확장을 고려할 때 후보지만 이번 국내 서비스에는 우선순위가 낮습니다.

Places 데이터는 저장·캐시·표시 조건을 확인해야 하며, 지도에 표시하는 Places 결과에는 Google 지도 사용 등의 정책이 적용됩니다. 서로 다른 제공자 데이터를 자유롭게 섞지 않습니다. 공식 정책

### 최종 기본안과 확인 사항

- **카카오 지도 + 자체 검수 장소 DB.**
- 경로 계산은 직접 구현하지 않고 외부 길찾기 연결.
- 지도 스타일은 허용된 SDK 범위에서 구현.
- 브라우저용 키는 도메인 제한.
- 서버 API 키는 서버에서만 사용.
- 캐시·저장·출처 표시는 API별 이용 조건 확인 후 확정.
- 쿼터와 승인 여부는 팀 계정 콘솔에서 확인.

이번 문서는 사용량과 계정 조건을 확정하지 않았으므로 정확한 비용은 제시하지 않습니다.

## 7. 사용자 참여와 SNS 요소

### 4주에 포함

- 관심 장소 저장.
- 장소 링크 공유.
- 사진 후기.
- 정보 오류 제보.
- 관심 장소 변경 알림.

### 제외

- 팔로우·DM·채팅.
- 독립적인 SNS 피드.
- 출석·미션.
- 무분별한 인기 랭킹.
- 추가 반응 기능은 우선 제외.

### 선택 이유

사용자 참여는 **정보 탐색을 보완**해야 합니다. 이용자가 적어도 공식 정보와 지도만으로 기본 가치가 있어야 합니다.

공유 화면은 다음을 담습니다.

- 장소명·대표 이미지.
- 지역·종목.
- 장소 상세 링크.

개인의 위치·식별값을 링크에 넣지 않습니다.

### 신뢰·조작 대응

- 공식 정보·제보·후기를 시각적으로 구분.
- 현재 열람 인원을 인기순 근거로 바로 사용하지 않음.
- 신고·작성 속도 제한.
- 운영자가 만든 소개를 사용자 후기처럼 게시하지 않음.
- 정보가 부족한 장소를 허위 이미지·가짜 반응으로 채우지 않음.

시설에는 공식 페이지 유입·오류 수정 창구라는 가치가 있을 수 있습니다. 그러나 실제 업체 참여 의사와 효과는 **미확인**입니다.

## 8. 사진과 숏폼 영상

### 결정: 사진 포함, 사용자 영상 업로드 제외

사진은 위치 분위기·시설 외관·접근 동선 확인에 충분한 시작점입니다.

영상은 서핑 파도, 입수 접근, 활동 구간처럼 움직임이 중요한 상황에서 도움이 될 수 있지만 다음 작업이 추가됩니다.

- 형식·코덱·길이 검증.
- 인코딩·썸네일.
- 작업 실패·재처리.
- 모바일 재생 호환.
- 큰 업로드·전송량.
- 음원·초상권 검토.
- 신고와 삭제.

**4주에는 사진 기능을 완성하고, 실제 사용자에게 영상 부족 때문에 판단하지 못한 사례가 있는지 확인합니다.**

### 사진 기본안

- 후기당 최대 5장.
- 파일당 최대 5MB.
- JPEG·PNG·WebP.
- 실제 픽셀 수 제한.
- 서버에서 형식 확인·재인코딩.
- GPS 등 불필요한 메타데이터 제거.
- 썸네일과 상세용 크기 분리.

### 업로드 흐름

1. 회원이 파일 메타데이터로 권한 요청.
2. 서버가 수량·한도 확인 후 고유한 임시 경로 발급.
3. 브라우저가 저장소로 직접 업로드.
4. 서버가 실제 파일·소유권 검증.
5. 이미지 처리 완료 후 `READY`.
6. 준비된 미디어만 후기에 연결.

S3 Presigned URL은 직접 업로드에 사용할 수 있지만, URL 발급과 파일 검증은 별개입니다. AWS 공식 문서

### 저장·삭제

- 임시 원본은 비공개.
- 검증된 공개 이미지에만 배포 경로 제공.
- DB에는 파일 경로·소유자·상태 저장.
- 미완료 파일은 24시간 후 정리 제안.
- 후기 삭제 시 이미지 공개 경로 해제·저장소 정리.
- CDN 캐시 잔존을 고려해 짧은 캐시 또는 무효화 정책 마련.
- 오류 때문에 연결된 파일까지 지우지 않도록 삭제 전 참조 확인.

### 추후 영상 실험안

- 후기당 1개, 최대 15초·30MB.
- 허용 컨테이너뿐 아니라 코덱·디코딩 가능 여부 확인.
- 표준 재인코딩·메타데이터 제거·썸네일 생성 후 공개.
- 장소 상세 안에서만 재생.
- 자동 재생·자동 소리 없음.
- 별도 숏폼 피드는 만들지 않음.

이는 **4주 약속 범위가 아닌 후속 설계안**입니다.

## 9. 도메인·ERD 수준 설계

기본 관계는 다음과 같습니다.

**사용자 → 저장·후기·제보·신고·알림**

**장소 → 제공 종목 → 시즌**

**장소 → 출처·공지·사진 후기**

### 핵심 엔티티

1. **User**

   ID, 로그인 식별자, 비밀번호 해시, 닉네임, 역할, 상태, 생성·탈퇴 시각.

2. **Region**

   내부 ID, 상위 지역, 코드, 이름. 외부 제공자 지역 코드와 내부 코드를 분리.

3. **ActivityCategory / ActivityType**

   상위 분류와 세부 종목. 초기에는 고정 깊이로 단순화.

4. **Place**

   ID, 이름, 별칭, 소개, 주소, 좌표, 지역, 공식 URL, 게시 상태, 운영 정보 상태, 버전, 검토일.

5. **PlaceActivity / PlaceActivitySeason**

   장소·종목 연결과 해당 종목의 시즌.

6. **SourceRecord**

   출처 종류, 원본 ID, URL, 확인 필드, 원본 수정 시각, 검토 시각, 검토자, 이용 조건 메모.

7. **PlaceNotice**

   장소, 제목·본문, 중요도, 유효기간, 출처, 공개 상태.

8. **Favorite**

   사용자, 장소, 저장 시각, 알림 여부·활성화 시각.

9. **Review / MediaAsset / ReviewImage**

   작성자·장소·본문·방문일·종목·버전·공개 상태와 검증된 파일 연결.

10. **CorrectionRequest / ReviewReport**

    작성자, 대상, 사유·근거, 처리 상태, 처리자·사유.

11. **Notification**

    수신자, 이벤트 ID, 장소, 종류, 생성·읽음 시각.

12. **PlaceChangeEvent**

    공개된 중요 변경과 알림 생성 작업 상태. 간단한 DB 작업함 역할.

13. **AdminAuditLog**

    운영자, 대상, 작업, 사유, 시각.


### 주요 제약

- 사용자·장소 저장 조합 유일.
- 장소·종목 조합 유일.
- 알림 수신자·변경 이벤트 조합 유일.
- 사용자·후기 신고 중복 제한.
- 출처 종류·원본 ID 중복 제한.
- 후기 수정은 버전 기반 충돌 검사.

### 인덱스 후보

- 장소 게시 상태·지역·정렬값.
- 장소별 종목 관계와 종목별 장소 관계.
- 후기 장소·공개 상태·작성 시각.
- 관심 장소 사용자·장소.
- 알림 사용자·작성 시각.
- 미처리 변경 이벤트 상태·다음 시도 시각.

실제 쿼리의 실행 계획으로 확정합니다. 좌표 인덱스 하나로 모든 공간 검색이 해결된다고 가정하지 않습니다.

### 상태 전이

- 장소 게시: `DRAFT → PUBLISHED → HIDDEN`.
- 운영 정보: `UNKNOWN / CONFIRMED / TEMPORARILY_CLOSED / CLOSED`.
- 미디어: `PENDING → VALIDATING → READY 또는 FAILED`.
- 후기: `PUBLISHED → HIDDEN 또는 DELETED`.
- 제보: `SUBMITTED → REVIEWING → APPLIED 또는 REJECTED`.

### 영구·일시 상태

- **영구:** 장소·후기·저장·공지·제보·알림·이력.
- **일시:** SSE 연결·전경 열람 lease·마지막 갱신·송신 대기 상태.

## 10. 인증·권한·운영 보안

### 인증 기본안

**동일 도메인의 쿠키 기반 세션**을 추천합니다.

- Spring Security.
- 세션 쿠키 `HttpOnly·Secure·SameSite`.
- 로그인 시 세션 ID 갱신.
- 비밀번호 전용 해시.
- 로그인 시도 제한.
- 변경 요청 CSRF 검증.
- 로그아웃 시 개인 SSE 연결 종료.

소셜 로그인·JWT를 모두 추가하지 않습니다. 자체 로그인을 제공한다면 비밀번호 재설정까지 범위에 포함해야 합니다.

### 권한

- 본인 후기·파일만 수정·연결.
- 운영자 API는 별도 역할 검사.
- 개인 알림은 서버 인증 정보로 수신자 결정.
- 클라이언트가 보내는 사용자 ID를 권한 근거로 사용하지 않음.
- 공개 장소 정보와 운영자 메모 분리.

### 입력·파일·URL

- 후기 일반 텍스트 출력.
- 요청 본문·파일·페이지 크기 제한.
- 업로드 MIME 선언만 신뢰하지 않음.
- 외부 링크에 HTTP(S)만 허용.
- URL 확인 작업은 내부 주소·과도한 리디렉션 방어.
- 세션·서명 URL·비밀키·개인정보를 로그에 남기지 않음.

### 개인정보·약관

**설계 제안**

- 이메일·닉네임 등 필요한 계정 정보만 수집.
- 현재 위치는 기본적으로 브라우저에서 검색에 사용하고 장기 이동 이력 저장 안 함.
- 이용약관·처리방침 공개.
- 사진 게시 권한·초상권·신고·삭제 안내.
- 실제 동의가 필요한 항목은 목적별 구분.
- 약관 동의 버전·시각 보관.

개인정보 처리방침 공개와 개인정보 수집 동의는 같은 것이 아닙니다. 계약 이행 등 동의 외의 처리 근거가 있을 수 있으므로 모든 항목을 일괄 필수 동의로 만들지 않습니다. 개인정보위 안내

중요한 약관은 쉽게 확인하도록 제시해야 합니다. 약관법 제3조

출시 전에는 실제 운영 형태와 대상 연령에 맞춰 안내문을 확정합니다.

## 11. HTTP API

> 아래 경로는 2026-11-09 기획 초안의 표기입니다. 현재 도메인 REST API의 공통 접두사는 `/api/v1`이며, 구현 기준은 [Backend 공통 경로 안내](../../backend/README.md#도메인-api-공통-경로)를 따릅니다. 아래 기능별 API는 설계안이며 구현 완료 목록이 아닙니다.

모든 변경 API는 인증·CSRF·입력 검증을 적용합니다. 공개 읽기 API는 비회원 허용입니다.

## 12. 실시간 설계

### 방식 비교

- **주기 조회:** 가장 단순하지만 변화가 없어도 요청 발생. 수십 초 갱신이면 충분할 수 있음.
- **SSE:** 서버가 변경을 전달. 사용자 상태 갱신은 HTTP로 분리.
- **WebSocket:** 잦은 양방향 이벤트가 핵심일 때 적합. 현재 범위에서는 필요성이 상대적으로 작음.

### 결정: SSE + HTTP lease

열람 인원·공지·개인 알림은 서버→브라우저 메시지이므로 SSE를 기본안으로 선정합니다.

SSE는 서버에서 이벤트를 보내는 구조이며 EventSource 재연결을 지원합니다. 연결 수와 프록시 설정은 별도로 고려해야 합니다. MDN

Spring MVC에서는 `SseEmitter` 등 비동기 응답을 활용할 수 있습니다. Spring 공식 문서

### 연결 구조

- 탭당 SSE 연결 하나.
- 장소별 연결과 알림별 연결을 별도로 늘리지 않음.
- 상세에서 나가면 열람 등록 해제.
- 목록에 머무는 회원은 개인 알림만 연결할 수 있음.
- 로그인·로그아웃 시 인증 상태에 맞게 연결 재생성.
- 쿠키로 인증하고 URL에 인증 토큰을 넣지 않음.

### 열람 정의

> 상세 화면이 전경이고, 최근 열람 갱신에 응답한 브라우저·계정.
>
- 회원: 계정 기준.
- 비회원: 서버가 발급한 짧은 유효기간의 브라우저 식별자.
- 식별자를 바꾸거나 기기가 다르면 통합할 수 없음.
- 다른 사람 목록은 노출하지 않고 집계만 제공.

### 시간 제안

- 브라우저 전경 lease 갱신: 20초.
- 무응답 만료: 60초.
- 일시 끊김 유예: 10초.
- SSE 유지 신호: 약 15초.
- 인원 방송: 변경을 모아 최대 약 2초 간격.

**SSE 유지 신호는 서버→클라이언트 통신일 뿐, 사용자가 화면을 보고 있다는 증거가 아닙니다.** 전경 상태를 담은 HTTP 갱신과 구분합니다.

### 중복·재접속

- 연결마다 고유 ID.
- 사용자·장소별 활성 연결 집합을 관리.
- 같은 사용자의 탭이 여러 개라도 장소별 한 명.
- 탭 숨김은 즉시 비활성 전환 요청.
- 이전 연결 종료는 해당 연결만 제거.
- 만료 검사로 비정상 종료 정리.
- 로그인 전후 식별자를 정리해 잠시 두 명으로 남지 않게 처리.

### 이벤트

- `ready` — 연결 ID·서버 실행 ID.
- `presence.snapshot` — 장소·집계·시각·순서.
- `place.changed` — 장소·새 버전·변경 종류.
- `notification.created` — 알림 ID·장소.
- `heartbeat` — 전송 경로 유지 확인.

원문 전체·운영 메모는 보내지 않습니다.

### 누락·순서·복구

- 인원은 과거 변화를 재생하지 않고 최신 스냅샷 적용.
- 정보 변경은 버전이 큰 경우만 반영.
- 개인 알림은 DB에서 재조회.
- 연결 완료 후 스냅샷을 받고 그동안의 신호와 버전 비교.
- 모든 이벤트의 영구 재전송을 보장하지 않음.
- 느린 클라이언트에는 송신 큐 상한·타임아웃 적용.

브라우저 종료 상태에서는 SSE가 푸시를 보내지 않습니다.

### 장애·확장

- SSE 실패해도 목록·상세·공식 링크 유지.
- 재시도는 백오프·무작위 지연.
- 장기 실패 시 숫자 숨김 또는 ‘확인 불가’.
- 초기 단일 서버는 메모리 상태.
- 다중 서버는 공유 lease·이벤트 전달·세션까지 함께 설계.

## 13. 알림과 비동기 처리

### 알림 기준

**개인 알림 대상**

- 공식 운영 중단·종료.
- 중요한 주소·접근 안내 변경.
- 운영자가 중요 공지로 지정한 내용.

**개인 알림 제외**

- 오타·사진 순서 수정.
- 일반 후기 등록.
- 검수 전 제보.

열린 상세에는 일반 변경도 `업데이트됨`으로 알릴 수 있습니다.

### 수신 설정

- 저장과 알림 수신을 구분.
- 기본은 알림 꺼짐, 사용자가 중요 변경 알림을 선택.
- 장소별·전체 끄기.
- 처리 시점에 수신 설정이 유효하고, 이벤트 공개 전에 저장·알림을 켠 사용자 대상.

### 소규모 기본안

1. 장소·공지 변경과 `PlaceChangeEvent`를 같은 트랜잭션에 저장.
2. 스케줄 작업이 미처리 이벤트 조회.
3. 수신 대상에게 DB 알림 생성.
4. 접속 중이면 SSE로 알림 신호.
5. 실패 재시도, 반복 실패는 운영 목록.

알림의 유일성은 `(수신자, 이벤트)` 제약으로 보장합니다.

이는 작은 Outbox 성격의 작업함입니다. 단순 애플리케이션 이벤트보다 코드가 늘지만, 재시작 후 복구 근거를 남길 수 있습니다.

### Redis·Kafka 조건

- **Redis:** 다중 서버 접속 상태·공통 요청 제한·측정된 캐시 병목.
- **Kafka:** 이벤트 보존·독립 소비자·대량 재처리가 실제 요구일 때.

이번에는 Kafka 없이 알림 생성·재시작 복구를 완성합니다. 기술 실험을 추가한다면 단순 작업함과 동일 조건으로 비교해야 합니다.

## 15. 부하·정합성·복구 테스트

### 시험 조건

50명·200명·1,000명을 단계적으로 시도합니다. 각 단계의 지속 시간·행동 빈도·장소 수·데이터량·사양을 기록합니다.

**단순 연결 시험과 실제 행동 시험을 분리합니다.**

예시 혼합 부하:

- 60%: 상세 열람·lease.
- 30%: 분당 몇 차례 검색·페이지 이동.
- 10%: 저장·후기·제보.
- 사진 업로드는 별도 시나리오로 측정.

이는 실제 사용자 행동을 확인하기 전의 가정입니다.

### 시나리오

- 인기 장소 하나에 접속 집중.
- 여러 장소에 분산.
- 빠른 검색 조건 변경.
- 연결 유지 장시간 시험.
- 다수 재접속.
- 탭 중복·숨김·복귀.
- 업로드·후기 동시 요청.
- 서버 재시작.
- 지도 API 지연·오류.
- 알림 처리 중단·재시작.

### 도구

- HTTP: k6.
- SSE: 선택 버전과 호환되는 `xk6-sse` 확장 등으로 작은 검증부터.
- 브라우저: 실제 모바일·PC에서 화면·메모리·스크롤 시험.
- 외부 API: 모의 응답으로 내부 한계를 측정하고 실제 호출은 제한 내 별도 시험.

k6 기본 HTTP 호출만으로 실시간 SSE 이벤트 지연까지 검증했다고 간주하지 않습니다. SSE 확장의 설치·지원은 선택한 k6 버전과 실행 환경에서 확인합니다. 확장 저장소

### 목표 제안

고정된 서버·데이터·네트워크 조건에서:

- 내부 읽기 API p95 500ms 이내.
- 예상하지 못한 오류율 1% 미만.
- 열람 인원 반영 3초 이내.
- 연결 복구 후 상태 재조회 5초 이내.
- 중복 저장·중복 알림·권한 우회 0건.

목표 미달이면 실패를 숨기지 않고 병목과 한계를 기록합니다.

**병목 재현 → 지표·쿼리 확인 → 개선 하나 적용 → 동일 조건 재측정** 순서로 진행합니다.

## 16. 역할과 4주 완성 일정

### 4명 역할 제안

**A — 탐색 화면·지도 / 검색 계약 공동 담당**

- 2열 목록·지도·상세 이동.
- 검색 상태·모바일.
- 렌더링 성능.

**B — 장소·검색·데이터 운영**

- DB 모델·검색·마커.
- 출처·수집·검수.
- 운영자 장소 화면까지 담당.

**C — 회원·후기·미디어**

- 인증·권한·후기·파일.
- 저장·내 활동 화면 일부.
- 신고·계정 처리.

**D — 실시간·알림·배포**

- SSE·lease·알림.
- 배포·관측·부하 시험.
- 알림 화면·운영 작업 상태.

한 명이 모든 프론트나 모든 배포를 독점하지 않게 공동 검토자를 지정합니다. **장소 데이터 검수는 팀 전체가 나눠 수행**합니다.

### 1주차 — 범위·검증

- 샘플 장소 5곳과 데이터 권한 확인.
- 지원 범위·필수 항목·화면·API 확정.
- 지도·SSE·사진 업로드 작은 기술 검증.
- ERD·CI·초기 배포.
- 약관·처리방침 초안.

**완료:** 실제 장소를 검색·조회하는 최소 흐름이 배포 환경에서 동작.

### 2주차 — 전체 흐름

- 검색·목록·지도·상세.
- 로그인·저장·공유.
- 후기·파일 검증.
- 운영자 장소 관리.
- 기본 열람 인원.

**완료:** 팀 외부 사용자가 주요 기능을 처음부터 끝까지 이용.

### 3주차 — 운영·예외

- 제보·신고.
- 변경 알림·재시도.
- 권한·중복·재접속.
- 사용자 관찰.
- 부하·장애 시험.

**완료:** 주요 실패 상황과 운영 처리가 연결됨.

### 4주차 — 안정화

- 신규 기능 추가 중단.
- 모바일·검색·실시간 오류 수정.
- 데이터 재확인.
- 백업·복구·비용 점검.
- 테스트·시연·발표.

**완료:** 알려진 한계와 실제 측정 결과를 포함해 공개 운영 가능.

### 지연 시 축소 순서

1. 새 종목·지역 추가.
2. 검색 자동완성의 풍부한 추천.
3. 현재 열람 인원의 표시 빈도·세부 연출.
4. 거리순 등 추가 정렬.
5. 자동 외부 데이터 갱신 → 운영자 검수·수동 실행으로 단순화.

권한·파일 검증·신고 처리·기본 탐색·배포 안정성을 먼저 지킵니다. 4주 완성은 역할별 산정과 첫 주 기술 검증으로 재확인해야 합니다.

- 카카오 데이터의 실제 저장·재표시 허용 범위.

- 열람 인원과 변경 알림이 실제로 유용한지.

1. 공개할 지역·종목·데이터 목표.
