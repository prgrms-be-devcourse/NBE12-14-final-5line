## 1. 사전 준비 전략

### 기본 방향

- 개인 GitHub 저장소에서 사전 작업을 진행한다.
- Backend, Frontend, Infra를 하나의 저장소에서 관리하는 **Monorepo 구조**를 사용한다.
- 작업 단위별로 브랜치를 분리하고, 검증된 결과를 커밋한다.
- 공식 팀 저장소가 생성되면 필요한 코드를 선택적으로 이식한다.
- 사전 구현 결과는 팀의 최종 결정이 아니며, 팀원들과 논의 후 채택한다.

### 작업 원칙

1. 모든 영역을 상세 설계한 후 구현하는 방식은 사용하지 않는다.
2. 전체 작업 목록은 큰 단위로만 관리한다.
3. 작업 하나를 선택하여 필요한 사항만 논의하고 바로 구현한다.
4. Codex를 활용하여 실제 코드 작성 및 테스트를 진행한다.
5. 각 작업은 독립적으로 이식할 수 있도록 의존성을 최소화한다.
6. 이해하지 못한 코드를 그대로 도입하지 않고, 주요 설정과 동작 원리를 확인한다.

### 역할 분담

| 역할 | 담당 |
|---|---|
| ChatGPT | 작업 전략, 우선순위, 기술 선택 논의, 작업 범위 검토 |
| Codex | 실제 코드 작성, 환경 구성, 테스트, 구현 |
| 개발자 | 최종 판단, 구현 결과 검증, Git 관리 |
| 팀원 | 공식 프로젝트의 기술 스택 및 공통 규칙 최종 합의 |

## 2. 프로젝트 개요

### 서비스

**OUTPICK — 스포츠·액티비티 장소 탐색 서비스**

지역·종목·시즌에 맞는 활동 장소를 검색하고, 지도와 상세 정보, 사진 후기 등을 통해 방문할 장소를 선택하는 웹 서비스.

### 주요 기능

- 장소 검색 및 지도 탐색
- 지역·종목·시즌 필터
- 장소 상세 정보
- 회원 인증 및 권한 관리
- 관심 장소 저장
- 사진 후기 및 이미지 업로드
- 정보 오류 제보 및 신고
- SSE 기반 실시간 상태 및 알림

### 기술 구성 후보

| 영역 | 기술 |
|---|---|
| Backend | Java 25, Spring Boot 4.1.2, Spring Data JPA |
| Frontend | Next.js Static Export, TypeScript, Tailwind CSS, Axios, TanStack Query, Zustand |
| Database | MySQL, Flyway |
| Infra | AWS, Terraform, Docker |
| CI/CD | GitHub Actions |
| Monitoring | Actuator, Prometheus, Grafana |
| Performance Test | k6 |

기술 구성은 현재 기획서와 사전 논의를 바탕으로 작성한 초안이며, 팀 합의 후 변경될 수 있다.

UI 컴포넌트 라이브러리와 공통 스타일 규칙은 팀 합의가 필요한 상태이므로 마지막에 진행한다.

앞선 작업은 기본 HTML과 최소한의 Tailwind CSS 스타일로 검증한다.

**결정한 방향**

- 팀원들의 Next.js 학습 경험을 고려해 Next.js + TypeScript를 사용한다.
- 팀원들에게 익숙한 npm과 Tailwind CSS를 사용한다. 초기 프로젝트의 Node.js 기준은 26.13.0이며, 설치 방법은 강제하지 않는다.
- Next.js 실행 서버 없이 빌드한 정적 파일을 저장소와 CDN으로 제공한다.
- Spring Boot API 서버와 분리하고, 브라우저에서 API를 호출한다.
- Axios는 HTTP 통신과 공통 오류 처리를 담당한다.
- Zustand는 여러 컴포넌트나 페이지가 공유하는 클라이언트 상태를 담당한다. 관리 위치와 중복 저장 방지 원칙은 [Frontend 상태 관리 규칙](../frontend/README.md#상태-관리-규칙)을 따른다.
- TanStack Query는 서버 데이터의 캐시·로딩·오류 상태 및 갱신을 담당한다. 브라우저에서 실행하는 API 요청에는 Next.js 서버의 fetch 캐시가 적용되지 않는다.

**추가 논의 및 인증 연계**

- 장소 상세 URL은 `/places/detail/?id=123`으로 결정했다. Next.js Static Export에서 빌드 후 추가되는 장소도 같은 정적 페이지로 조회하는 방향이다.
- OUTPICK 공통 OG 태그를 제공하는 방향으로 두고, 장소별 OG 태그·검색엔진 노출 요구사항은 주요 기능 개발 후 팀과 논의한다.
- JWT·HttpOnly·Secure 쿠키 인증을 예상하되, 토큰 전달·갱신 방식은 인증 담당자와 합의한다.
- 쿠키 인증을 위한 CORS·SameSite·HTTPS·CSRF 대응은 인증 담당자 및 배포 담당자와 함께 정한다. 
  - 인증 구현 자체는 현재 Frontend 사전 준비 범위에 포함하지 않는다.
- UI·스타일 라이브러리는 아직 정하지 않았다.

- Nx, Turborepo 등 별도 모노레포 관리 도구는 우선 도입하지 않는다.
- 공식 팀 저장소의 최종 구조는 팀 합의에 따른다.

## 5. 브랜치 및 코드 이식 전략

### 사전 작업

- 개인 GitHub 저장소에서 작업한다.
- 작업별 브랜치를 생성한다.
- 하나의 브랜치에는 가능한 한 하나의 작업 목적만 포함한다.
- 작업이 완료되면 실행 및 테스트 결과를 확인하고 커밋한다.
- 서로 의존하는 작업은 기반 브랜치나 커밋을 명확히 관리한다.

### 공식 프로젝트로 이식

1. 팀장이 공식 GitHub 저장소를 생성한다.
2. 팀원들과 프로젝트 구조 및 공통 규칙을 합의한다.
3. 사전 작업 중 실제 프로젝트에 필요한 항목을 선택한다.
4. 파일 복사 또는 `git cherry-pick` 등 적합한 방법으로 반영한다.
5. 공식 저장소 환경에서 다시 빌드·테스트한다.
6. PR을 통해 검토 후 병합한다.

**주의사항**

- 파일 복사 방식은 단순하지만 기존 코드와 설정이 충돌할 수 있다.
- `git cherry-pick`은 커밋 간 의존성과 디렉터리 구조를 고려해야 한다.
- 사전 작업의 모든 코드를 반드시 이식할 필요는 없다.
- 공식 프로젝트의 코드와 설정을 우선한다.

## 8. 다음 작업

**다음 작업: Backend CI 구성 논의 (3.3 자동화)**

Backend·Frontend 공통 기반과 정적 빌드·로컬 HTTP 검증·사용자 브라우저 확인을 마쳤다. 다음 세션에서는 Java 25와 Testcontainers MySQL을 사용하는 Backend 테스트·빌드 CI의 실행 브랜치·이벤트·변경 경로 조건을 먼저 논의한다. "작업하자" 확인 전에는 Workflow를 작성하지 않는다.

Backend CI 검토·커밋 후 Frontend CI를 별도 작업으로 진행한다. Frontend CI는 Node 기준 버전·npm ci와 린트·타입 검사·테스트·정적 빌드를 대상으로 하며 빌드용 API 주소를 정해야 한다. Dockerfile·이미지 업로드·CD는 이후 작업이다.

Zustand는 공유할 UI 상태가 확정될 때까지 보류한다. UI·스타일 기반 구성은 팀 논의 후 진행한다. 운영 환경·Infra·Database 후속 설정·모니터링·성능 테스트 항목은 미완료 상태를 유지한다.

이후 작업은 고정된 순서에 얽매이지 않고, 의존성과 프로젝트 시작 시점의 필요성을 고려하여 선택한다.

**최종 목표:** 공식 프로젝트 시작 시 팀원들이 기능 개발에 바로 착수할 수 있도록, 검증된 공통 기반 코드를 선택적으로 이식할 수 있는 상태를 만든다.
