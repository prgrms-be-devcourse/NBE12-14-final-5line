# 수집된 운영 안내 — DB의 TourAPI 장소 일괄 연결

## 현재 범위

DB의 `tour_api_import`에 연결된 장소의 이용시간·휴무일·문의전화를 TourAPI `detailIntro2`에서 수동 수집해 상세에 연결한다. 최초 플라이스테이션 파일럿에서 DB 전체 대상으로 확장했으며, 최신 develop의 500곳 선정 목록과 수집·공개 정책은 변경하지 않는다. `operatingInfo`는 **수집된 참고 안내**이며, 기존 `operationStatus`(운영 여부), 장소 검수일 및 `notices`(검수된 공지)를 대체하지 않는다. 제공되지 않은 정보는 추정하지 않는다.

이번 단계는 최초 저장·표시까지다. 재수집한 값의 변경 비교, 변경 후보 이력, 운영자 반영·보류 화면, 스케줄러, 실시간 알림은 구현하지 않는다. 이미 저장된 운영 안내는 재실행해도 SKIPPED로 유지하며 검수·대조 정보를 덮어쓰지 않는다.

## 로컬 실행

수집 명령은 활성 프로필을 강제하지 않는다. 외부 `SPRING_PROFILES_ACTIVE`를 존중하고, 지정이 없을 때는 `application.yaml`의 기본 `local`을 사용한다. `prod` 단독이면 로컬 설정 파일을 읽지 않으므로 DB·메일·비밀번호 재설정 필수 설정을 실행 환경에서 제공해야 한다. 현재 배포 Compose의 `local` 설정 자체를 변경한 것은 아니다.

Java 25, 실행 중인 로컬 MySQL 및 루트 `.env`의 기존 MYSQL 설정과 `TOUR_API_KEY`(Decoding)를 사용한다.

```powershell
powershell -ExecutionPolicy Bypass -File ./backend/scripts/import-tourapi.ps1 -Task importPlaceOperatingInfo
```

맥·Linux에서는 프로젝트 루트에서 로컬용 `.env`의 환경변수를 적용한 뒤 실행한다. 기존 장소 수집이 먼저 완료되어 있어야 한다.

```bash
set -a
source .env
set +a
./backend/gradlew -p backend importPlaceOperatingInfo --no-daemon
```

공식 안내와의 대조 기록은 `backend/scripts/review-flystation-operating-info.sql`을 로컬 DB에 별도로 실행한다. 2026-11-16에 확인한 값에 대한 기록이며 서버 시작이나 수집 명령이 자동 적용하지 않는다.

DB 수집 이력의 콘텐츠 ID 기본키 순으로 100건씩 읽어 전체 대상을 처리한다. 코드에 장소 ID를 추가하지 않으며 기존 수집 이력과 연결된 장소만 대상이다. 대상 500곳 전체가 로컬 DB에 들어 있지 않으면 실제 DB의 대상 수만 처리한다.

외부 HTTP는 DB 트랜잭션·잠금 밖에서 순차 호출하고, 새 호출 전에 250ms 간격을 둔다. 기존 전송 계층의 공식 호스트 제한·리다이렉트 금지·타임아웃·응답 크기 제한·키가 포함된 예외 제거 정책을 재사용한다. 성공 코드와 대상 ID·유형(28)을 확인하고 HTML을 일반 텍스트로 변환한다. 서버 시작과 CI에서는 외부 API를 호출하지 않는다.

장소별 결과는 `CREATED`(최초 저장), `SKIPPED`(기존 안내 보존), `NO_DATA`(정상 성공의 결과 0건 또는 세 항목 모두 미제공), `FAILED`(호출·응답·저장 실패)로 출력한다. 일부 항목만 비면 해당 항목은 null로 저장한다. 오류가 나도 다음 장소를 계속 처리하며 오류·인터럽트가 있으면 종료 코드 1을 반환한다. 원본 예외/응답/키가 포함된 URL을 로그에 출력하지 않는다.

기존 안내는 HTTP 호출 전과 저장 트랜잭션 안에서 각각 확인한다. 검수 상태·대조 기록·수집 값은 덮어쓰지 않는다. 재실행하면 저장된 곳은 외부 호출도 건너뛰고 실패·미제공 대상만 다시 조회한다. `NO_DATA`를 별도 DB 이력으로 저장하지 않으므로 화면에서는 기존의 안내 없음 문구를 유지한다. 자동 갱신·재시도 스케줄러는 포함하지 않는다.

EC2에서는 기존 배포 설정과 TourAPI 키를 사용하는 임시 컨테이너로 실행한다. 새 명령이 포함된 Backend 이미지를 먼저 배포해야 한다.

```bash
docker compose --env-file .env -f compose.deploy.yaml -f compose.places.yaml \
  run -T --rm --no-deps --entrypoint java backend \
  -Dloader.main=com.outpick.domain.place.importer.TourOperatingInfoCommand \
  -cp /app/app.jar org.springframework.boot.loader.launch.PropertiesLauncher
```

V10은 `place_operating_info`를 추가한다. 장소 PK/FK와 TourAPI 수집 이력 FK로 최초 수집 장소에 연결하고, 수집 값과 수집일을 저장한다. HTTP 실패는 기존 데이터를 변경하지 않고, DB 저장 실패는 해당 트랜잭션을 롤백한다. 초기 수집은 UNVERIFIED이며 `verified_at`은 null이다. 기존 장소·사진 마이그레이션과 후기·관리자 API는 수정하지 않는다. 팀 ERD에 이 추가 테이블을 반영해야 한다.

## 상세 API와 화면

`GET /api/v1/places/{placeId}`에 다음 필드를 가진 nullable `operatingInfo`가 추가됐다.

- `operatingHours`, `restDays`, `contactPhone`: 수집한 참고 값. 제공되지 않은 개별 항목은 null이다.
- `sourceUrl`: 키가 포함되지 않은 공공데이터 서비스 안내 페이지.
- `collectedAt`: 최초 수집 결과가 저장된 서울 시간. 최신성이 확인된 시각이 아니다.
- `verificationStatus`: UNVERIFIED(미검수), NEEDS_REVIEW(확인 필요), VERIFIED(검수된 안내).
- `verifiedAt`: 값의 검수가 완료된 시각. VERIFIED일 때만 값이 존재하도록 DB CHECK를 적용했다. 현재 파일럿은 null이다.
- `reviewNote`, `officialSourceUrl`, `comparedAt`: 공식 안내와 대조한 결과·공식 안내 링크·대조일. 대조했다는 사실만으로 값이 검수 완료된 것으로 처리하지 않는다.

운영 안내가 없으면 ‘아직 수집된 운영 안내가 없습니다’로, 일부 항목만 비었으면 ‘제공된 정보 없음’으로 구분한다. ‘운영 정보’와 ‘운영 공지’를 분리하고, 기존 고정 문구 ‘운영시간·이용 조건·휴장 여부는 미확인’은 제거했다. 공지가 비어 있으면 우리 DB 기준 ‘등록된 운영 공지가 없습니다’로 표시한다. 운영 안내는 장소 조회에서 함께 LEFT JOIN해 상세 쿼리 수 5개를 유지한다. 비공개·검수 전 장소의 운영 안내도 공개하지 않는다.

## 2026-11-16 대조 결과

수집 응답에는 평일 10:30~19:30, 주말/공휴일 09:30~19:30, 매주 월요일 휴무, 문의전화 1855-3946이 있다. [공식 체험 안내](https://flystation.kr/usage/usage_020100.html)의 평일 예약 시간은 11:30~20:30이며, 같은 페이지 하단 운영시간도 본문과 다르다. 전화번호는 일치한다. 어느 시간이 최신인지와 월요일 실제 운영 여부는 확정하지 않는다.

이 차이는 `scripts/review-flystation-operating-info.sql`로 명시적으로 로컬에 기록한다. 해당 응답 값과 일치하고 아직 대조·검수하지 않은 행만 NEEDS_REVIEW로 변경한다. 공개 값이나 공지를 덮어쓰지 않는다. 대조일은 날짜만 확인한 기록이라 2026-11-16 00:00:00으로 저장하고 화면에는 날짜만 표시한다. 이 기록은 팀 운영자 계정의 승인 이력이 아니다. 실제 검수일은 null로 남긴다.

검증은 공급자 응답 검증·HTML 변환·결측 처리, 최초 저장·재실행 시 보존·롤백, 수집일과 검수일의 분리, 비공개 장소 접근 제한 및 화면 상태 표시를 대상으로 한다.

## 2026-11-23 로컬 검증

- 로컬 DB 전체 백업 후 실행했다. 기존 TourAPI 장소 15곳 중 6곳이 최신 500곳 목록에 포함돼 있어 장소 494곳을 추가 수집했다. 기존 목록 밖 9곳은 보존했으므로 수집 장소는 총 509곳이다. 최신 develop의 공개 SQL을 실행해 신규 지도 검증용 494곳도 로컬에서 조회되도록 했다. 500곳 선정 목록과 공개 SQL은 이번 코드 변경에 포함하지 않았다.
- 운영 안내는 신규 373곳 저장, 기존 14곳 건너뜀, 미제공 122곳, 실패 0곳으로 종료됐다. 저장된 안내는 총 387곳이며 신규 안내는 모두 UNVERIFIED다. 기존 플라이스테이션의 NEEDS_REVIEW 기록은 유지됐다.
- 제공기관의 결과 0건/모든 항목 미제공을 정상적인 미제공으로 처리했다. 공식 안내의 값이나 다른 장소의 값으로 대신 채우지 않았다. 실제 저장 항목의 수집일은 검수 완료일이 아니다.
- 기존 장소·출처·사진·운영 안내의 전체 행을 수집 전 스냅샷과 비교해 동일함을 확인했다. 배포 DB에는 실행하지 않았다.
- 로컬 임시 서버에서 공개 장소 509곳과 신규 운영 안내 10곳의 상세 API 응답을 확인했다. 미검수 상태, 검수일 null, 수집일의 존재를 확인했다.
- 백엔드 전체 빌드 및 테스트 157건 통과(실패·오류·건너뜀 0). 새 테스트는 한글 `@DisplayName`을 사용한다. DB 페이지 조회, 1,001건 대상의 페이지 순회 모의 테스트, 장소별 실패 격리, 재실행 시 HTTP 생략·검수 값 보존, 프로필 보존·운영 프로필의 로컬 관리자 미생성을 포함한다. 외부 API를 실제 1,001번 호출한 검증은 아니다.
