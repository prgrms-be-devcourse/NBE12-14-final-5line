# 회원 인증 계약

- `POST /api/v1/auth/login`: 이메일·비밀번호를 확인하고 15분짜리 JWT 액세스 쿠키(`outpick_access`)와 7일짜리 리프레시 쿠키(`outpick_refresh`)를 발급한다. 두 쿠키는 `HttpOnly`, `SameSite=Lax`이며 HTTPS 배포에서는 `Secure`다. JWT나 리프레시 토큰 원문을 JSON 응답에 담지 않는다.
- `POST /api/v1/auth/refresh`: 리프레시 쿠키를 검증하고 새 액세스·리프레시 쿠키를 발급한다. 리프레시 값은 JWT가 아닌 256비트 난수이며 DB에는 SHA-256 해시만 저장한다. 이전 리프레시 토큰은 즉시 폐기한다. 폐기된 토큰의 재사용을 감지하면 같은 발급 계열을 폐기한다. 유효하지 않으면 401과 쿠키 삭제를 반환한다.
- `POST /api/v1/auth/logout`: 현재 로그인 토큰을 폐기하고 해당 회원의 발급된 모든 액세스·리프레시 토큰을 무효화한다. 로그아웃 후에는 자동 로그인이 되지 않는다.
- 변경 요청은 `GET /api/v1/auth/csrf`로 얻은 헤더명·토큰을 함께 전송한다. CSRF 쿠키는 인증 세션이 아니며 서버는 `JSESSIONID`를 발급하지 않는다.
- 프런트엔드는 회원 API의 401에 한 번만 갱신을 시도하고 성공하면 원래 요청을 재시도한다. 동시 401은 갱신 요청 하나를 공유한다. 로그인·비밀번호 재설정 등 인증 API의 401은 자동 갱신하지 않는다.
- 비밀번호 변경과 회원 탈퇴는 기존 토큰을 무효화한다. 운영자 역할과 계정 상태는 매 요청마다 DB에서 확인한다.

배포에서는 `.env.example`의 `AUTH_JWT_SECRET_BASE64`에 안전하게 생성한 32바이트 이상 서명키의 Base64 값을 지정한다. 실제 값은 저장소에 커밋하지 않는다. HTTPS 배포는 `compose.https.yaml`을 함께 적용하여 인증 쿠키의 `Secure`를 켠다. 기존 세션 쿠키는 인증에 사용되지 않으므로 배포 후 기존 로그인 사용자는 다시 로그인해야 한다.
